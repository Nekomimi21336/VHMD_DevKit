# VHMD Link のネイティブ部分(`link/`)

VHMD のドライバとは別のソフトウェアとして、VHMD Link(PC とヘッドセットをつなぐアプリ)のうち速さが要る部分と、試験用の道具を Rust で置いています。標準ライブラリだけで書いているので、ネットからの取得なしにビルドできます(`cargo build --release --offline`)。

| クレート | 実行ファイル | 役割 |
|---|---|---|
| `proto` | — | PC ↔ ヘッドセットの取り決め(ポート、映像のヘッダー 64 バイト、小さな JSON の読み書き) |
| `relay` | `vhmdlinkrelay.dll`(と単独の `vhmd-link-relay`) | ヘッドセットとドライバの間のデータの通り道(姿勢・映像・振動・PC の検出)。PC のアプリが自分のプロセスに DLL として読み込み、設定と状態だけをやりとりする |
| `sim` | `vhmd-link-sim` | PC の上で動くヘッドセットの代役。ヘッドセットなしで VHMD Link 全体を試す |

```powershell
cd link
cargo build --release          # target/release/ に 2 つの exe
cargo test                     # 取り決めの単体テスト
```

## vhmd-link-relay(データの通り道)

- PC のアプリ(`python -m vhmd_client.link`、`VHMD Link.exe`)と `headset_bridge` は、これがあれば自動で使います(`--native auto|on|off`)。無ければ今までどおり Python で中継します。`VHMD Link.exe` には同梱(`tools/build_link_exe.py` がビルドして入れる)。
- DLL として PC のアプリの中で動かす(`vhmd_link_relay_start`)。中継のスレッドはネイティブなので Python が止まっても止まらず、ネットワークのポートは PC のアプリのものになるので、Windows のファイアウォールに新しいプログラムとして聞かれない(単独の exe で動かすと、初回に「Windows セキュリティ」の確認が出て、許可するまで Wi-Fi のヘッドセットがつながらない)。
- 姿勢: ヘッドセットから UDP(Wi-Fi)/ TCP の行(USB)で受け、そのままドライバへ。ヘッドセット自身のメッセージ(`headset` / `link_stats` / `link_timing`)だけ PC のアプリに渡す。
- 映像と音: ヘッドセットの接続ごとにドライバのエンコーダー(127.0.0.1:39583)につなぎ、設定の行を送って、届いたものをそのまま流す。送信が詰まればビットレートを下げ、空けば戻す。
- 振動: ドライバからの振動をヘッドセットへ。ドライバへの問い合わせ(PC のアプリから)も姿勢と同じソケットから送る(ドライバは最後に送ってきた相手に振動を送るため)。
- PC のアプリとは 127.0.0.1 の UDP でやりとりする(1 行目に `control 127.0.0.1:ポート` を出す)。PC のアプリから 10 秒連絡が無ければ自分で終わる。

### Python との比較(`tests/integration/link_load_test.py`、45 秒ずつ、ヘッドセットなし)

PC のアプリの中で、別のスレッドが Python のロックを 40 ms ほど持ち続ける処理を時々したとき(画面の更新が重い・ガベージコレクションなどに相当):

| | Python で中継 | vhmd-link-relay |
|---|---|---|
| 新しい画像 | 63.4 回/秒(繰り返し 366) | 71.4 回/秒(繰り返し 3) |
| 姿勢の転送の最大 | 366 ms | 0.58 ms |
| 映像の転送の最大 | 24.6 ms | 5.3 ms |
| 姿勢を送ってからそれで描いた映像が届くまで(平均) | 23.1 ms | 20.8 ms |

負荷が無いときの差は小さい(姿勢の転送 平均 約 90 → 60〜70 µs、映像の中継 約 0.2 ms は同じ。PC 内の TCP の分)。効くのは、Python 側が止まっても姿勢と映像が止まらないこと。

## 映像を UDP と誤り訂正で送る(実験的)

TCP では Wi-Fi で 1 つのパケットが落ちると、送り直されるまで後ろが全部待たされます(数十 ms)。UDP では、映像 1 枚(と音)を約 1,200 バイトずつに分け、Reed-Solomon の誤り訂正のパケットを足して送ります。落ちた分は待たずに組み立て直し、組み立てられなかった画像があれば、次のキーフレームまで画像を飛ばしてキーフレームを頼みます(250 ms ごとに頼み直す)。

- 取り決め: `proto/src/udp.rs`(パケットの形、GF(2^8)・Cauchy 行列の Reed-Solomon、128 断片ごとのブロック)。ヘッドセット側の受け取りは C++ の `headset/android/src/udp_video.h` で、PC の単体テスト(`tests/unit/test_udp_video.cpp`)が Rust の作ったパケット(`proto/testdata/udp_vectors.bin`、41 個を落としたもの)を組み立てられるか確かめる。
- キーフレームは誤り訂正を 2 倍(40% 以上)にする。音のパケットを落としてもキーフレームは頼まない(パケットに種類が入っている)。
- ビットレート: UDP は送信が詰まらないので、ヘッドセットが報告する「組み立てられなかった画像」が毎秒 1 枚を超えたら 20% 下げ、10 秒なければ 10% 戻す。
- 使い方: PC のアプリの「パフォーマンス」→「映像を UDP と誤り訂正で送る」と「誤り訂正 20 / 30 / 50%」(`headset_bridge --udp-video --fec 30`)。ネイティブのデータの通り道(この DLL)が必要。ヘッドセットは受け取り用のポートを `headset` メッセージの `video_udp_port` で知らせる。
- `vhmd-link-sim --udp --loss 2 --burst 3` で、わざとパケットを落として試せる。結果(30 秒〜40 秒、3840 × 1920 HEVC 40 Mbit/s):

| わざと落とす | 誤り訂正 | 新しい画像 | 組み立て直した | 復号の誤り |
|---|---|---|---|---|
| なし | 30% | 71.0 回/秒 | 0 | 0 |
| 5%(ばらばら) | 30% | 70.6 回/秒 | 3,016 枚 | 0 |
| 2%(3 つずつ続けて) | 30% | 69.3 回/秒 | 1,959 枚 | 0 |
| 1%(10 個ずつ続けて) | 50% | 24 回/秒 | — | — |

長く続けて落ちる電波(10 個ずつ)にはまだ弱い。

## vhmd-link-sim(ヘッドセットの代役)

本物の VHMD Link と同じように、PC を探し(ブロードキャスト、無ければ 127.0.0.1)、毎フレーム(72 Hz)頭・両手の姿勢を送り(頭は左右 ±30°・上下に動く)、自分の表示の説明・統計・フレームのタイミングを送り、映像と音を受け取ります。72 Hz の表示を模して、毎回いちばん新しい画像を出す(繰り返し・捨てた枚数・表示までの待ちを数える)ので、PC 側のタイミング合わせもこれ相手に働きます。復号はしない(`--check` で保存した映像を最後に ffmpeg で復号して確かめる)。

```powershell
link\target\release\vhmd-link-sim.exe --seconds 30                    # Wi-Fi と同じ UDP で
link\target\release\vhmd-link-sim.exe --pc 127.0.0.1 --usb --check --snapshot frame.png --json out.json
```

1 つの時計(この PC)で測るもの:

- transit: ドライバが映像を送り出してから届くまで(中継 + ネットワーク)
- pose → frame: 姿勢を送ってから、その姿勢で描かれた映像が届くまで(中継、SteamVR、描画、圧縮、転送)。映像のヘッダーに描画に使った頭の姿勢が付いているので、送った姿勢と照らし合わせる
- 先読み: PC が求めたとき(`status` の `predict`)、本物と同じやり方で測って姿勢を先の時刻で送る

注意: 本物のヘッドセットが同じ PC につながっていると取り合いになります。試すときは `headset_bridge --usb-only`(127.0.0.1 だけで待つ)と `--pc 127.0.0.1 --usb` を組み合わせると、Wi-Fi のヘッドセットは加わりません。
