# VHMD Link(ヘッドセット側アプリ)

単体型ヘッドセット(まず Pico 4 Ultra)で動く OpenXR のネイティブアプリです。VHMD を SteamVR の HMD のまま使い、実機のヘッドセットをその「入力」と「表示」にするためのものです。

| 段階 | 内容 | 状態 |
|---|---|---|
| 1 | 頭・両手の姿勢と入力を VHMD に送る(Wi-Fi が基本、USB は予備) | 動作確認済み(Pico 4 Ultra、Pico OS 5.15.7) |
| 2 | VHMD が描いた映像をヘッドセットに表示する(描画時の姿勢で補正、視野角・解像度をヘッドセットに合わせる) | 動作確認済み |
| 3 | ドライバ側でマニュアル(ヘッドセット)とオート(自動操作)を SteamVR を止めずに切り替える | 動作確認済み |
| 4 | PC とヘッドセットをつなぐ普通のアプリにする: 接続用と開発用の 2 つ、PC のアプリ(トレイ常駐)、インストーラー、接続画面 | 動作確認済み(インストーラーは未実行) |
| 5 | 仕上げ: PC とヘッドセットのフレームのタイミング合わせ、Wi-Fi の低遅延ロック、ビットレートの自動調整、90 Hz、AV1 | 動作確認済み(90 Hz はヘッドセット側の設定待ち) |

## 2 つのエディション

同じソースから 2 つの APK を作ります。並べてインストールできます。

| | VHMD Link(接続用) | VHMD Link Dev(開発用) |
|---|---|---|
| パッケージ / APK | `com.vhmd.link` / `vhmd-link.apk` | `com.vhmd.link.dev` / `vhmd-link-dev.apk` |
| ヘッドセットの中 | 映像だけ。PC につながるまでは接続画面 | 映像の下に統計(表示・受信 fps、Mbit/s、待ち時間、リンク、音、振動、操作権) |
| SteamVR のコントローラーの見た目 | 名前入りの形(`labeled`) | 色付きの軸(X 赤・Y 緑・Z 青、白い線が前) |
| PC のアプリ | 普通の表示 | 開発者向けの表示が自動で出る |

ヘッドセットがメッセージ `headset` の `edition` で名乗り、PC のアプリがドライバの見た目(`config` の `render_models`)を合わせます。

## ヘッドセットの中の表示

- **接続画面**: PC の映像が出ていないとき(起動直後、PC や SteamVR を待っているとき、映像が 1 秒止まったとき)は、正面に案内のパネルを出します。PC を探している / PC「名前」に接続(Wi-Fi のアドレスか USB)/ SteamVR を待っている / 映像を待っている、このヘッドセットの IP アドレスとアプリの版。パネルは視線を 35° 以上外すと正面に戻ってきます。
- **お知らせ**: 操作権がヘッドセット以外(オートなど)に移ったとき(「X + A 長押しで取り戻せます」)、取り戻したとき、X + A を押している間。
- 文字は Android の文字描画(JNI で `android.graphics.Canvas`)で描くので日本語も出ます。システムの言語が日本語なら日本語、それ以外は英語。パネルは OpenXR のクワッドレイヤー(文字が変わったときだけ描き直す)。
- PC からは約 1 秒ごとに状態 `{"type":"status","pc":名前,"steamvr":…,"driver":…,"control":…}` が届きます(振動と同じ経路)。

## しくみ

```
ヘッドセット: VHMD Link ──姿勢・入力(Wi-Fi: UDP 39580 / USB: TCP 39580)──> PC: headset_bridge ──UDP──> VHMD ドライバ
                       <──H.264 映像(TCP 39581)────────────────────────── PC: headset_stream <── VHMD のプレビュー
```

### つなぎ方(Wi-Fi が基本)

1. アプリは起動すると LAN に `VHMD-DISCOVER` をブロードキャスト(UDP 39582)し、PC の `headset_bridge` が答えます。IP アドレスの入力は要りません。
2. 見つかれば Wi-Fi: 姿勢・入力は 1 配列 = 1 データグラムの UDP(遅れた古いパケットで後続が待たされない)、映像は TCP。
3. 見つからなければ USB: `adb reverse` 経由の TCP(127.0.0.1)。1 配列 = 1 行。
4. アドレスを固定したいときは、ヘッドセットの `/sdcard/Android/data/com.vhmd.link/files/pc_address.txt` に PC の IPv4 アドレスを書く(`adb push`)と、探さずにそこへつなぎます。

- ヘッドセット内の床のグリッドの色: 緑 = Wi-Fi、水色 = USB、赤 = 未接続。
- VHMD ドライバは PC 内(127.0.0.1)でだけ待ち受けたままで、LAN に開くのは `headset_bridge` のポート(UDP 39580・39582、TCP 39580・39581)です。LAN 上のどの機器からもつなげるので、信頼できるネットワークで使うか、`--usb-only` で PC 内だけにします。

### 姿勢と入力(段階 1)

- アプリは毎フレーム(72 Hz)、OpenXR の STAGE 空間(床が原点、+Y 上、-Z 前方、メートル)で頭(VIEW)と両手(grip)の姿勢を取り、VHMD のプロトコルのメッセージ(`pose` / `input`)を 1 行の JSON 配列にして送ります。STAGE 空間は SteamVR の立位の座標と同じ向きなので、そのまま送ります。
- 入力: トリガー(値・タッチ・クリック)、グリップ、スティック(x / y・押し込み・タッチ)、A / B / X / Y、メニュー。Pico 4 のコントローラー定義(`XR_BD_controller_interaction`)と Touch の定義の両方でバインドします。
- 振動: SteamVR のアプリがコントローラーを振動させると、`headset_bridge` 経由でヘッドセットのコントローラーが振動します(長さ・周波数・強さをそのまま渡す)。
- ヘッドセットの中には床のグリッド(PC につながっていれば緑、つながっていなければ赤)と、コントローラーの軸を表示します。

### 映像(段階 2)

- PC(既定): ドライバの中で圧縮する(`driver/src/windows/stream_encoder.*`)。合成器が出した両目のテクスチャを GPU 上で並べ、D3D11 のビデオプロセッサーで縮小と NV12(BT.709 リミテッドレンジ)への変換をし、Media Foundation のハードウェアエンコーダー(このPC では AMD の `AMDh265Encoder` / `AMDh264Encoder`)に GPU テクスチャのまま渡す。CPU への読み出しも Python も通らない。描画時の姿勢を付けて 127.0.0.1:39583 に出し、`headset_bridge` はそれをそのままヘッドセットへ流す。既定は HEVC・40 Mbit/s・1 目はヘッドセットの幅(`--codec`、`--bitrate`、`--eye-width`)。
- PC(予備、古いドライバや Linux): VHMD のダイレクトモードのプレビュー(両目を並べた RGBA)を ffmpeg に渡し、GPU のエンコーダー(既定 `h264_amf`)で H.264 にする。ffmpeg からは RTP で受け取り、RTP のマーカービットでフレームの終わりが分かった時点で送る(フレームの区切り待ちによる遅れが無い)。
- 色: リミテッドレンジの BT.709 で送る。フルレンジのままだと、ヘッドセットの GPU の YUV 変換がリミテッドレンジとして扱い、暗部がつぶれる(背景 13/255 が 0 になっていた)。
- ヘッドセット: MediaCodec(ハードウェアデコーダー、低遅延モード、H.264 / HEVC)で復号して AImageReader に出し(出力は専用のスレッドがすぐに取り出す)、その AHardwareBuffer を EGLImage として外部テクスチャにそのまま貼る(コピーなし)。各目の半分を全面に描き、レイヤーの視野角には VHMD が描いたときの値(PC が SteamVR から取って最初に送る)を使う。
- 補正(リプロジェクション): ドライバがフレームごとに「そのフレームを描いた頭の姿勢」(合成器の SubmitLayer の姿勢)をプレビューのヘッダーに書き、PC はそれをフレームと 1 対 1 で(ffmpeg は `-fps_mode passthrough`)送ります。ヘッドセットは表示レイヤーの姿勢をその姿勢(+目の位置)にするので、Pico の合成器が今の頭の姿勢との差を補正します。デコーダーのタイムスタンプ(フレーム番号 × 11111 µs)で、表示する画像がどのフレームかを引き当てます。

### 遅れの内訳(測定、2026-10-21)

Pico 4 Ultra・Wi-Fi・HEVC 3840 × 1920・40 Mbit/s・72 Hz、1 フレームあたり(平均 / 最大)。ドライバの `status` の `stream`(`submit_ms` / `encode_ms` / `encoder_ms`)、ヘッドセットの `link_stats`(`decode_ms`)、`headset_bridge` の表示(relay / pose fwd)、PC のアプリの開発者向け表示で見られます。

| 区間 | 前 | 今 |
|---|---|---|
| 合成器のスレッドでの処理(縮小・色変換を GPU に積む) | 0.27 / 0.58 ms | 0.25 / 0.49 ms |
| 圧縮(Submit から送り出しまで) | 9.4 / 12.0 ms | **6.95 / 8.7〜9.3 ms**(AMF、うち圧縮器の中 6.7 ms)。Media Foundation では 8.8 / 11 ms |
| Python の中継(映像 1 フレーム) | 0.20 / 1.25 ms | 同じ(GUI の中でも 0.19 ms、p99 0.3〜0.7 ms) |
| Python の中継(姿勢 1 メッセージ) | 0.09〜0.12 / 0.4 ms | 同じ |
| ヘッドセットの復号 | 11.95 / 22.4 ms | 7.7〜8.5 / 11〜15 ms |
| 表示までの待ち(タイミング合わせの目標) | 5.4 ms | 5.4 ms |

- 圧縮: AMD の GPU では AMD 純正の AMF を超低遅延の用途(`ULTRA_LOW_LATENCY`)で直接使う(`driver/src/windows/amf_encoder.*`、ヘッダーは `third_party/amf`、実行時は AMD のドライバに入っている `amfrt64.dll` を読み込む)。1 フレームずつ渡してすぐ受け取る。AMF が無い GPU・古いドライバでは自動で Media Foundation に戻る(`headset_bridge --encoder mf` で固定もできる)。H.264 / HEVC / AV1 とも動作(自己テストで 3840 × 1920 を取りこぼしなし)。2 基のエンコーダーで分担する設定(`MULTI_HW_INSTANCE_ENCODE`)・速度寄りのプリセットは、この GPU では差が出なかった。
- Media Foundation の経路も、出力を 1 ms ごとに見に行っていたのを、イベントを待つ専用のスレッドにした(9.4 → 8.8 ms)。
- 復号: Qualcomm のデコーダーに「復号した順に出す」(`vendor.qti-ext-dec-picture-order.enable`)を指定。並べ替えのために 1 枚持たれていた分(約 4 ms)が消えた。
- Python の部分(中継・姿勢の転送)は 1 フレームあたり 0.15〜0.2 ms ほどで、全体(約 23 ms)の 1% 前後。CPU は 72 fps で 1 コアの約 5%。ここを Rust などに書き換えても縮むのは 0.2 ms ほど。
- 全体の目安(1 フレーム、平均): 合成器 0.25 + 圧縮 6.95 + 中継 0.15 + Wi-Fi 数 ms + 復号 8.5 + 表示までの待ち 5.5 ≒ 23 ms(前は約 29 ms)。

### なめらかさ(段階 5)

- **フレームのタイミング合わせ**: PC(VHMD の vsync)とヘッドセットの 72 Hz はそれぞれの水晶で動くので、位相が少しずつずれ、映像が表示の締め切りの直後に届く時間帯は 1 枚待たされて次の 1 枚が捨てられる(新しい画像が 72 中 50 前後まで落ちていた)。ヘッドセットは画像が表示まで待った時間を表示周期上の円平均で 0.5 秒ごとに送り(`link_timing`)、`headset_bridge` がドライバの `display_sync` に渡し、ドライバが vsync を少しずつずらして待ち時間を周期の 0.4(72 Hz で 5.6 ms)に保つ。
- **Wi-Fi の低遅延ロック**: ヘッドセットの Wi-Fi は省電力のためにまとめて受け取り、映像が 2 枚ずつ届いていた(毎秒 11 回前後)。アプリの実行中は Android の `WIFI_MODE_FULL_LOW_LATENCY` のロックを持つ(`WAKE_LOCK` 権限)。
- 結果(Wi-Fi、2 分ずつ、表示 72 Hz のうち新しい画像の回数): タイミング合わせ + ロック **71.0**、タイミング合わせだけ 62.5、ロックだけ 57.7、どちらもなし 53.9。
- **ビットレートの自動調整**: ヘッドセットへの送信が詰まる(1 秒のうち 20% 以上待たされる)と 30% 下げ、空いていれば 3 秒ごとに 15% ずつ設定値まで戻す。詰まった値の 85% を 30 秒は超えない。ドライバのエンコーダーは送信中に新しいビットレートを受け付ける(再接続なし)。送信バッファを約 60 ms 分に絞り、詰まったときに何秒分もためない。確認: Wi-Fi で 500 Mbit/s を指定すると 350 → 245 → 171 に下げ、以後 約 190〜210 Mbit/s で安定(300 Mbit/s までは詰まらずに届いた)。`--fixed-bitrate` で無効。
- **リフレッシュレート**: PC のアプリで 72 / 90 Hz を選ぶとヘッドセットに伝え(`status` の `refresh`)、ヘッドセットが切り替えたら VHMD も SteamVR を止めずに同じレートにする(`config` の `refresh_rate`)。Pico 4 Ultra は本体の設定(ディスプレイのリフレッシュレート)が 72 Hz のままだと 72 Hz しか出さない(OpenXR が 72 だけを返す)ので、90 Hz は本体の設定を 90 Hz にしてから。
- **AV1**: `--codec av1` / PC のアプリの圧縮方式。RX 7900 XTX の `AMDav1Encoder` で動き、ヘッドセットは `video/av01` で復号する。ただし 1 目 1920 では SteamVR 中の圧縮が 毎秒 52 枚ほどで頭打ち、1 目 1440 では 72 枚出るがヘッドセットの AV1 デコーダーの出し方が不揃いで新しい画像は 50 前後。既定は HEVC のまま。AV1 の圧縮器がない GPU では HEVC に切り替わる。

### 音(PC → ヘッドセット)

- ドライバが、PC の既定の出力デバイスで鳴っている音を WASAPI のループバックで取り込み、映像と同じ接続で送ります(16 ビット、PC の出力のサンプリングレート、最大 2 チャンネル、10 ms ずつ)。ヘッドセットは AAudio(低遅延モード)で再生し、約 40 ms たまってから鳴らし始め、150 ms を超えてたまったら新しい分を捨てて遅れを戻します。
- PC のスピーカーからも同じ音が出ます(必要なら PC 側をミュート)。マイク(ヘッドセット → PC)は、PC に仮想の録音デバイス(仮想オーディオケーブル)を入れる必要があるため未対応。
- 確認: 48 kHz ステレオ、毎秒 100 パケット(10 ms)、途切れ 0、捨てた分 0(Wi-Fi)。
- ヘッドセットがすぐにつなぎ直したとき(アプリの再起動など)、新しい接続に音の形式が送られず無音になっていたのを直した(接続ごとに送る)。

### 視野角・解像度を合わせる

アプリは 2 秒ごとに自分の表示(目ごとの視野角、目の位置、推奨解像度、リフレッシュレート)を `{"type":"headset",...}` として送り、`headset_bridge` が `%LOCALAPPDATA%\VHMD\headset.json` に保存します。VHMD の視野角と違うときは案内を出すので、一度だけ次を実行します(SteamVR が再起動します)。

```powershell
python -m vhmd_client.mode vhmd --headset      # 元に戻すときは --no-headset
```

一度 `--headset` にすると、その後の `mode vhmd`(FPS 操作ツールの切り替えボタンも)でもヘッドセットの値を使い続けます(`%LOCALAPPDATA%\VHMD\headset_applied`)。

- SteamVR の設定 `vhmd_display`: 目ごとの視野角(`leftTanLeft` ... `rightTanDown`、ドライバが非対称な視野角に対応)、`renderWidth` / `renderHeight`、`ipdMeters`、`displayFrequency`。
- VHMD の設定のプロファイル: ダイレクトモード、`display.refreshHz` と `preview.fps` をヘッドセットのリフレッシュレートに、`preview.maxEyeWidth` をヘッドセットの目の幅に。プロファイルは `%LOCALAPPDATA%` にあり切り替えのたびに作り直すので、ドライバをビルドし直してインストール済みの設定が既定値に戻っても消えません。

### マニュアルとオート(段階 3)

VHMD は SteamVR の HMD のまま、誰が動かすかだけを切り替えます(SteamVR も VR アプリも止まりません)。

```powershell
python -m vhmd_client.control auto       # 自動操作のプログラムに渡す
python -m vhmd_client.control manual     # 人に戻す
python -m vhmd_client.control auto --devices left_hand right_hand   # 手だけ渡す
python -m vhmd_client.control            # 今の状態と、送ってきている送り手
```

- 送り手はメッセージに `src` を付けて名乗ります。VHMD Link と FPS 操作ツールは `manual`、自動操作は `VHMDClient(source="auto")`。
- 操作権を持たない送り手のメッセージは捨てられます(数は `control` / `status` に出る)。操作権が移るとき、前の送り手が押していたボタン・トリガーは離した状態に戻ります。
- 自動操作に渡すときの応答と `control` の問い合わせには各デバイスの最新の姿勢が入るので、引き継ぐ側は今の位置から続けられます。FPS 操作ツールの「マニュアルに戻す」はこれを使い、自動操作が置いた位置から操作を再開します。
- ヘッドセットで X と A を 1.5 秒押し続けると、操作権を `manual` に取り戻します(装着している人がいつでも戻れるように)。
- 確認(Pico 4 Ultra、Wi-Fi): 操作権なしではヘッドセットの姿勢、`control auto` で自動操作の姿勢(1.0, 1.5, -0.5)に即座に切り替わり、`control manual` で戻る。そのあいだ相手側のメッセージは捨てられた(ヘッドセット 540 件、自動操作 30 件)。X + A の長押しは、装着しての確認がまだ。

## 使い方

### リリースの zip から(Windows)

1. ヘッドセットで開発者モードと USB デバッグを有効にし、USB でつなぐ(アプリを入れるときだけ)。PC とヘッドセットは同じ LAN に。
2. 展開したフォルダで:

   ```powershell
   powershell -ExecutionPolicy Bypass -File tools\install_link.ps1 -Start     # -Apk dev で開発用、-Apk both で両方、-Desktop でデスクトップにも
   ```

   ドライバを SteamVR に登録し、スタートメニューに「VHMD Link」(zip の `VHMD Link\VHMD Link.exe`)を作り、USB でつながっていればヘッドセットにアプリを入れます。Python は要りません(exe が無いときだけ Python 3.9 以上で動かす)。元に戻すのは `tools\uninstall_link.ps1`。
3. PC で「VHMD Link」を開き、ヘッドセットで VHMD Link を起動すると自動でつながります(Wi-Fi が基本、USB ケーブルでも)。Windows のファイアウォールが VHMD Link の通信を確認してきたら、プライベート ネットワークを許可します。

### PC のアプリ(VHMD Link)

```powershell
python -m vhmd_client.link            # pythonw clients\python\vhmd_link.pyw ならコンソールなし。--dev で開発者向けの表示
```

単体の exe(Python の入っていない PC 向け)は PyInstaller で作ります。`dist\VHMD Link\VHMD Link.exe`(フォルダごと配る、約 34 MB)ができ、リリースの zip に入ります。キーボード・マウス操作ツールも同じ exe(`"VHMD Link.exe" --fps`)。

```powershell
python -m pip install pyinstaller pillow
python tools/build_link_exe.py            # --onefile で 1 ファイル(起動が少し遅い)
```

- ヘッドセットの接続(機種、Wi-Fi のアドレス / USB、アプリの版)と SteamVR の状態を表示。
- ヘッドセットがつながったら SteamVR を起動(VHMD モードのときだけ。設定で切れる)。SteamVR が実機 HMD モードなら「VHMD モードにする」、VHMD の視野角・解像度がヘッドセットと違えば「ヘッドセットの画面に合わせる」(どちらも SteamVR を再起動するので確認を出す)。
- 画質(20 / 40 / 60 / 80 Mbit/s)、圧縮方式(HEVC / H.264)、動き(遅れを最小に / なめらか)。変えるとヘッドセットがつなぎ直して(約 1 秒)反映。
- 開発者向けの表示: PC とヘッドセットの統計、操作権、ログ、「操作をヘッドセットに戻す」、キーボード・マウス操作ツールの起動。
- ウィンドウを閉じても通知領域(トレイ)で動き続けます。アイコンのクリックで開く、右クリックで終了。「Windows の起動時に開く」で自分のユーザーのスタートアップに登録。
- 設定は `%LOCALAPPDATA%\VHMD\link_settings.json`。
- USB ケーブルを後から挿しても、10 秒以内に `adb reverse` をかけ直してつながります。

### 開発中(リポジトリから)

1. ビルドとインストール(初回は `--fetch-loader` で OpenXR ローダーを Maven Central から取得。既定で 2 つのエディションを作る):

   ```powershell
   python headset/android/build_apk.py --fetch-loader --install            # --edition dev / link で片方だけ
   ```

2. PC で `python -m vhmd_client.link`、またはコンソールで中継だけ:

   ```powershell
   python -m vhmd_client.headset_bridge            # USB を使わないなら --no-adb、Wi-Fi を使わないなら --usb-only
   ```

3. SteamVR は VHMD モード(`python -m vhmd_client.mode vhmd`)にしておくと、VHMD の HMD とコントローラーがヘッドセットに合わせて動きます。

## ビルド

Gradle は使いません。`build_apk.py` が次を行います。

- NDK + CMake(Ninja)で `libvhmdlink.so` をビルド
- `aapt2 link` で AndroidManifest.xml から APK を作り、`.so` を無圧縮で追加して `zipalign -P 16`
- ローカルの Android デバッグ鍵(`~/.android/debug.keystore`)で `apksigner` 署名

必要なもの: Android SDK(NDK・build-tools・platform)、CMake、Ninja、JDK。OpenXR ローダーは Khronos の `openxr_loader_for_android-1.1.63.aar`(SHA-1 を確認)を `headset/.cache` に置きます(Git 管理外)。

## 確認したこと(2026-10-21、Pico 4 Ultra A9210、Pico OS 5.15.7、Android 14)

- Khronos のローダーがシステムのランタイムブローカー経由で Pico のランタイム(`com.pico.xr.openxr_runtime`)を読み込み、拡張 69 個。Pico 4 のコントローラー定義あり。
- 目ごとのスワップチェーンは 1920 × 1920。セッションは FOCUSED まで進み、72 回/秒で PC に届く(約 58 KiB/s)。
- VHMD モードの SteamVR で、`VHMD-HMD-0`・`VHMD-CTL-L/R` がヘッドセットの姿勢になった。
- 映像: 2160 × 1200(両目並び)を 20〜26 Mbit/s で送り、ヘッドセットで受信・復号 約 60 回/秒、表示の更新 約 52 回/秒(表示は 72 Hz)。PC 側の入力が約 60 回/秒で頭打ち(プレビューを Python でコピーして ffmpeg に渡している部分)。ヘッドセットの画面キャプチャと PC の元画像で、向き・左右・明るさが一致。
- Wi-Fi(5 GHz、Wi-Fi 5、866 Mbit/s、RSSI -32 dBm): USB の転送を消した状態で、アプリが PC(192.168.0.4)を自動で見つけ、姿勢・入力 72 回/秒(UDP)、映像 約 63 fps・20 Mbit/s(TCP)。映像を流している間の往復遅延(ping)は平均 2 ms(1〜4 ms)。何も流していないときは平均 38 ms(ヘッドセットの Wi-Fi 省電力)。
- USB だけ(`--usb-only`)でも従来どおり動く。
- Pico 4 Ultra の表示: 1920 × 1920 / 目、72 Hz、視野角 ±47.5°(左右対称、目の向きの傾きなし)、IPD 72.0 mm(本体の設定値)。`--headset` の後、SteamVR から見た VHMD の視野角も ±47.5°、72 Hz、IPD 72 mm になり、ヘッドセットで映像がレンズの範囲いっぱいに出る。
- 補正: 表示したフレームの 100% が描画時の姿勢付き。プレビューの姿勢は Pico から送った頭の位置と一致(置いた状態で確認。動かしたときの見え方は未確認)。
- 映像 2880 × 1440(1 目 1440)を 72 fps・約 23 Mbit/s で送る。最初は約 50 fps だった。原因はドライバのプレビューの間引き(「前回から 1/72 秒以上」の判定で、少し早く来たフレームを落としていた。締め切り方式に変えて 72 / 72)と、PC 側で共有メモリの読み出し(3.5 ms)と ffmpeg への書き込み(11 ms)を順番にしていたこと(別スレッドに分けた)。
- ヘッドセット側(Wi-Fi、2026-10-21、30 秒ずつ): 受信・復号は 72 フレーム/秒、補正(描画時の姿勢付き)100%。表示 72 Hz のうち新しい画像に替わる回数と、復号から表示までの待ち:

  | `--buffer` | 新しい画像 | 前の画像のまま | 待ち(平均 / p95) |
  |---|---|---|---|
  | 0(既定、最新を表示) | 68.1 回/秒 | 3.9 回/秒 | 6.1 / 10.0 ms |
  | 1(1 枚ためる) | 71.0 回/秒 | 1.0 回/秒 | 18.1 / 25.5 ms |

  1 枚ためると表示はほぼ 72 になり、遅れが約 12 ms(ほぼ 1 フレーム)増える。頭の回転は補正で隠れるので、増えるのは画面の中の動きとコントローラーの反応の遅れ。`python -m vhmd_client.headset_bridge --buffer 1` で切り替え(接続のたびにヘッドセットへ渡す)。
- ドライバ内の圧縮(2026-10-21、Wi-Fi): HEVC 3840 × 1920(1 目 1920)を 72 fps・約 40 Mbit/s、ドライバの出力間隔は 13.9 ms で一定、フレームの抜けなし。ヘッドセットで受信・復号 72、新しい画像 63〜66 回/秒、復号から表示まで 平均 3 ms。前の Python + ffmpeg の経路(2880 × 1440 の H.264、約 23 Mbit/s)より 1 目あたりの画素が 1.8 倍。
- 復号した画像の取り出しを、次のフレームを入れたあとにしていたため、間に合わなかったフレームが 1 つ待たされて 2 枚ずつ出ていた(新しい画像 52〜55 回/秒)。専用のスレッドで取り出すように直した。残りの抜け(6〜9 回/秒)は PC と ヘッドセットの 72 Hz の位相が合っていないため(後でフレームのタイミング合わせをする)。
- 最初は新しい画像が 62.9 回/秒だった: 描画のループがデコーダーの出力(AImageReader)を取りに行く前に、次のフレームが前のフレームを上書きしていた。画像ができた時点で読み出し側のスレッド(AImageReader のリスナー)が受け取り、自前のキューに入れるように直した。
- ヘッドセットの受信・復号・表示のフレームレートと補正の割合は 2 秒ごとに PC に送られ、`headset_bridge` の表示に出る(Wi-Fi だけのときは logcat が見られないため)。
- ドライバをビルドするとインストール済みの `vhmd_config.json` がリポジトリの既定値に戻る。ストリーミング用の値は `--headset` のプロファイルで設定するので影響しない。
